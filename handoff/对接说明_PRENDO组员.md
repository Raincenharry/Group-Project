# 对接说明：给负责 PR-ENDO 的组员

你负责两件事：

1. 用 VR-Caps 组员导出的训练数据训练 PR-ENDO。
2. 按 VR-Caps 组员给的光照参数，用训练好的模型生成改变光照后的模拟图像，交给 Yutong。

VR-Caps 组员会在 Unity 里渲染同样光照下的真实图像，也交给 Yutong。两组图像由 Yutong 比较。你不会收到那些真实图像，也不需要它们。

建议同时读一遍《对接说明：给负责 VR-Caps 的组员》，里面有数据格式的完整定义。

## 1. 你会收到什么

VR-Caps 组员每次交付一个 `VRCaps_<场景名>_v<版本号>` 文件夹：

```
VRCaps_colon1_v1/
├── transforms.json              训练相机
├── train_views/0000.png         训练图像
├── depth_train/0000.exr         训练深度
└── relight/
    ├── export_settings.json     Unity 导出设置
    ├── transforms_relight.json  要生成模拟图像的帧
    └── lights.json              光照配置和每帧的光源位姿
```

另外，Yutong 会给你一个数：聚光衰减指数 n，见第 4.3 节。

### 1.1 训练数据的约定

格式沿用 PR-ENDO 官方合成数据集 RotateColon 的格式。

| 项 | 约定 |
| --- | --- |
| `transform_matrix` | 4×4 的相机到世界（c2w）矩阵，OpenGL / Blender 约定：相机 +X 朝右，+Y 朝上，看向 −Z |
| `camera_angle_x` | 水平视场角，弧度。相机无畸变，像素是正方形，主点在图像中心 |
| `file_path` | 帧号，不补零。文件名是补零到 4 位的帧号 |
| 训练图像 | 8 位 PNG。由线性图像"截断到 0–1 后取 1/2.2 次方"得到，没有经过色调映射 |
| 训练深度 | EXR，单通道。线性的 z 深度（沿光轴的距离），单位和相机位置一致 |
| 测试集 | 没有。视频的所有帧都用于训练，不做新视角测试 |
| 光源 | 相机中心的点光源，白色，强度固定。下文称为基准光源 |

### 1.2 光照参数的约定

`transforms_relight.json` 列出要生成模拟图像的帧。这些帧都是训练帧，帧号和相机矩阵与 `transforms.json` 里的同一帧相同。

`lights.json` 有两部分。`configs` 是光照配置，一共 25 种；`frames` 给出每个（配置，帧）下光源的世界坐标位姿。字段的完整定义在 VR-Caps 说明的第 6.5 节。你主要用到这些：

| 字段 | 含义 |
| --- | --- |
| `configs[].id` | 配置编号，比如 `L3_r0.25` |
| `configs[].type` | `point`（点光源）或 `spot`（聚光灯） |
| `configs[].intensity_scale` | 光强相对基准光源的倍数 s |
| `configs[].color_scale` | 红、绿、蓝三个通道相对基准光源的倍数 c |
| `frames[].config`，`frame` | 配置编号和 4 位帧号 |
| `frames[].light_pos_world` | 这一帧里光源的世界坐标 p_L |
| `frames[].light_dir_world` | 这一帧里光束方向的单位向量 d_L |
| `frames[].valid` | false 的条目跳过，不生成图像 |

光源的位置和方向与 `transform_matrix` 在同一个世界坐标系里，可以直接使用，不需要再转换。

## 2. 你要自己准备的

1. **PR-ENDO 的运行环境。** 代码在 GitHub `SanoScience/PR-ENDO`。请固定一个提交，并记下提交号。
2. **VR-Caps 数据的读取代码。** 官方代码只支持 C3VD 和 RotateColon 两种数据。
3. **初始点云。** PR-ENDO 训练需要一个初始点云，对方不提供。你用训练帧的深度图和相机位姿反投影生成。
4. **训练脚本。**
5. **按光照参数生成图像的脚本。** 见第 4 节。

写读取代码时，官方代码里有几处需要留意：

- 数据类型是按路径名判断的。`scene/__init__.py` 里，路径含 `C3VD` 走 C3VD 读取，含 `Rotate` 走 RotateColon 读取，其他路径直接报错。
- RotateColon 的读取函数是 `scene/dataset_readers.py` 里的 `readRotateSceneInfo`，可以作为起点。它假设：
  - 深度在 EXR 的 `ViewLayer.Depth.Z` 通道里。这是 Blender 的通道名，Unity 导出的名字会不同，实际名字记在 `relight/export_settings.json`。
  - 深度读出后除以 1.4。这个数是 RotateColon 专用的，你需要决定 VR-Caps 用多少，并记录下来。
  - 初始点云在数据文件夹下的 `init_point_cloud.ply`，只用其中的 x、y、z。
  - 测试相机在 `transforms_test.json`，测试图像在 `test_views_1/`。我们的数据没有这两项，你的读取代码要能在没有测试集的情况下工作。
- 读取时会把 c2w 的 Y、Z 两列取反，从 OpenGL 约定转成 PR-ENDO 内部的约定。
- 训练参数可以从官方 `run_all.sh` 里 RotateColon 的那一组开始。

## 3. 训练

没有特殊要求，按 PR-ENDO 的正常流程训练。训练完后在训练帧上渲染，和原图比较，计算 PSNR、SSIM、LPIPS，确认模型能还原这段视频。

如果还原程度明显偏低，或者渲染图和原图肉眼就能看出差别，先和 VR-Caps 组员一起排查数据，不要往下做。

## 4. 生成模拟图像

### 4.1 要生成什么

对 `lights.json` 的 `frames` 里每个 `valid` 为 true 的条目，生成一张图像：用该帧的相机位姿，按该配置的光照渲染。

同一个配置如果有 `noshadow` 和 `shadow` 两个版本，你只生成一张。PR-ENDO 不计算阴影，两个版本对你来说是一样的。

### 4.2 光照参数怎么传给 PR-ENDO

PR-ENDO 的光照计算在 `scene/gaussian_model.py` 的 `compute_lighted_rgb` 里。这个函数本身支持把光源和相机分开，官方的 `render_light_rotations.py` 是一个使用示例。

| `compute_lighted_rgb` 的参数 | 取值 |
| --- | --- |
| `camera_center` | 该帧的相机中心 |
| `light` | 训练得到的光源参数，其中第 0 项（光强）乘以 s |
| `light_center_sep` | p_L |
| `light_rot` | 点光源：不传（None）。聚光灯：任意一个第三列等于 d_L 的 3×3 旋转矩阵 |
| `spotlight_attenuation_power` | 聚光灯：n。点光源：不起作用 |
| `iter` | 训练的最终迭代数。必须大于 1000，否则不会启用漫反射 MLP |

三点注意：

- **点光源不能传 `light_rot`。** 一旦传了，代码会把光束轴线背后的半个空间置为全黑，即使 n = 0 也一样。
- **颜色倍数 c 在函数外面处理。** PR-ENDO 假设白光。函数输出的颜色已经取过 1/2.2 次方，所以要先取 2.2 次方转回线性，按通道乘以 c，再截断到 0–1 并取 1/2.2 次方。
- **不要改 `compute_lighted_rgb` 内部的计算。** 我们要比较的就是这个函数的原始行为。

### 4.3 聚光衰减指数 n

PR-ENDO 的聚光灯亮度按"偏离光束轴线角度的余弦的 n 次方"衰减。Unity 的聚光灯用内外锥角描述，两者不是同一个公式。n 由 Yutong 根据 Unity 渲染的图像算出来给你，你直接使用，不要自己调整。

拿到 n 之前，可以先生成所有点光源配置的图像（L0、L1、L3、L4、L5）。只有 L2 的 9 种配置需要 n。

### 4.4 输出格式

```
pred_<数据文件夹名>_<运行编号>/
├── record.json
└── <配置编号>/
    ├── 0100.png     显示空间，8 位
    └── 0100.exr     线性空间，浮点
```

| 文件 | 内容 |
| --- | --- |
| `<配置编号>/<帧号>.png` | 模型最终输出的图像，和训练图像同一种编码，分辨率相同 |
| `<配置编号>/<帧号>.exr` | 同一张图像取 2.2 次方后的线性值，RGB 三通道浮点，不截断到 8 位 |
| `record.json` | 见下表 |

配置编号和帧号与 `lights.json` 完全一致。运行编号用 `日期-时间`，比如 `20261120-1530`。

`record.json` 的内容：

| 字段 | 内容 |
| --- | --- |
| `dataset` | 用的数据文件夹名，含版本号 |
| `prendo_commit` | PR-ENDO 官方仓库的提交号 |
| `code_commit` | 你自己代码的仓库和提交号 |
| `train_command` | 完整的训练命令 |
| `iteration` | 用的是哪一步的模型 |
| `depth_scale` | 第 2 节提到的深度缩放系数 |
| `spot_power` | 用的 n |
| `train_psnr`，`train_ssim`，`train_lpips` | 训练帧的还原指标 |
| `notes` | 训练或渲染中出现的任何异常，以及和本文件要求不一致的地方 |

## 5. 每个阶段你做什么

### 阶段 0：对方回答六个问题

VR-Caps 组员会先回答：渲染管线、默认光源类型、次表面散射、视场角和分辨率、真实尺寸、能否导出 EXR。你需要确认两件事：

- 训练用的光源能改成相机中心的点光源。PR-ENDO 假设光源向各个方向发光相同，用聚光灯训练会把光束的明暗分布错误地学进材质。
- 图像没有畸变。有畸变的话，要求对方先去畸变，或者你在读取代码里处理。

### 阶段 1：试跑包

对方先交一个小包：约 50 张训练帧，2 个主要帧和 5 个标定帧的光照参数。目标是把整条流程走通。

1. **结构检查**：文件齐全，训练图像和训练深度数量相同，帧号能和 `transforms.json` 对上。
2. **位姿和深度检查**：生成初始点云，用 MeshLab 或 CloudCompare 打开。应该是一条完整、不重影的肠道。散乱或重影说明相机位姿或深度的约定有错，这是最常见的问题。
3. **读取检查**：用你的读取代码加载数据，确认帧数正确，图像和深度的分辨率一致。
4. **短训练**：训练几千步，确认损失下降，渲染出的图像正常。
5. **生成模拟图像**：用短训练的模型，对试跑包里的全部条目生成图像，按 4.4 的格式输出。

交出：

- 给 VR-Caps 组员一份回执，逐项写通过或不通过。不通过的项要写清现象和你的判断。
- 给 Yutong 试跑的模拟图像。Yutong 会用它检查光源位置和方向的正负号有没有弄反，并把结果告诉你。

### 阶段 2：完整训练

对方交完整的训练数据。按第 3 节训练，并把训练帧的还原指标告诉 VR-Caps 组员和 Yutong。

### 阶段 3：生成全部模拟图像

对方交完整的光照参数。对全部条目生成图像，按 4.4 的格式交给 Yutong。

如果对方说明只有光照参数变了、训练数据没变，不用重新训练，只需要重新生成图像。

## 6. 版本规则

- 对方每次重新导出都换版本号，不覆盖旧文件夹。
- 你每次生成图像都用新的运行编号，不覆盖已经交出的输出。
- 模型用哪个数据版本训练、图像按哪个版本的光照参数生成，都写进 `record.json`。
